# 2026-09-05 CI 运行修复

## 已定位的问题

1. 组合 `user-closure-e2e` 连续调用 Dashboard / Investigation 门禁时，旧脚本终止的是 npx/pnpm 或 shell 外层 PID，Next 开发子进程继续占用应用目录。后续 Next 日志显示 `Another next dev server is already running`，浏览器报 `ERR_CONNECTION_REFUSED`。
2. 文档更新删除了 `Phase 3` 历史阶段说明，触发数据契约文档断言；`data-contract` 与随后调用相同测试的 `intake-e2e` 同时失败。
3. 将脚本回归纳入 CI 时发现两项已有测试滞后：job 清单仍是 15 项，Dashboard 摘要测试仍模拟已移除的 HTTP 读取实现。现分别更新为 16 项和实际的本地 JSON 读取/拒绝行为。
4. 首轮修复运行 `33892693014` 中 15 个 job 通过；组合 job 的 API 全量阶段为 322 passed、1 failed。失败测试跨多个 `transaction()` 调用复用 PostgreSQL 临时表，连接池改派物理连接后临时表不可见。该组合 job 在失败时已运行约 43 分钟，继续重复所有独立门禁也会挤压 45 分钟的最终浏览器闭环预算。

## 修复

- 新增标准库服务监督器 `scripts/run_service.py`，为每个服务创建独立进程组，接收 TERM/INT 后清理自有组；超过五秒仍未退出的子进程再强制终止。
- 三个浏览器门禁直接启动监督器，退出时同时终止并等待 API/Web 监督器；正常结束、失败和中断均走清理。
- 移除组合脚本的全局 `pkill`，保留用户其他开发服务。
- 数据契约文档补回准确的 Phase 3 实现说明，不放宽断言。
- static-python CI 增加脚本测试，覆盖子进程端口释放、TERM/INT、非相关服务不受影响、退出状态及全部门禁清单。
- 事务回滚测试改用唯一命名的普通探针表，并在 `finally` 中删除；测试现在验证跨池化连接的提交与回滚行为。
- CI 的组合 job 只执行用户闭环专属浏览器验收；契约、全量 API 和前端静态检查继续由独立 job 负责。此前只随全量 API 间接运行的 Dashboard 8 项与 Publishing 14 项 API 测试，分别并入对应独立 job，保持 323 项 API 测试的整体覆盖。
