# FLOW 完整决策日志

状态定义：

- **有效**：当前设计仍然采用；
- **被取代**：曾经考虑或确认，但后来被明确修改；
- **未来**：长期方向，未进入 V1；
- **未决**：尚未进入最终选择。

## D001 产品不是单一驾驶舱

- 状态：有效
- 决定：长期产品方向是 AI 原生的 Finance Intelligence OS；驾驶舱、Excel 分析和报告只是消费、分析和发布界面。
- 原因：参考资料共同显示，真正价值来自数据可信、统一指标、专业诊断、Finding、证据和行动/发布闭环。

## D002 V1 产品定位

- 状态：有效
- 决定：V1 是面向物流供应链企业 Finance BP 的月度经营分析工作台。
- 原因：需要用一个真实行业和完整工作流验证产品，而不是直接建设通用平台。

## D003 部署方式

- 状态：有效
- 决定：不把纯本地离线作为产品前提，架构保持部署方式中立。
- 原因：用户说明本地离线只是实现手段，不是目标；Web、应用或其他部署都可接受。

## D004 项目名称

- 状态：有效但品牌释义未决
- 决定：工程和工作名称使用 FLOW；长期类别名使用 Finance Intelligence OS。
- 原因：FLOW 具有财务逻辑、经营和工作空间的联想，但正式英文展开不影响 V1。

## D005 首版行业与业务

- 状态：有效
- 决定：Dashboard、Investigation、AI 和报告共同读取已发布且不可变的 Analysis Run；下游不得重新执行分析公式或修改 Finding 排名。
- 原因：保证所有界面和输出使用同一事实、Driver、证据和策略版本。

## D034 Phase 6 Dashboard 读取边界

- 状态：有效
- 决定：浏览器只通过 typed `GET /api/v1/dashboard/overview` 读取只读投影；该投影只消费相互绑定的已发布 Metric Snapshot、Analysis Run 及治理元数据。
- 禁止：浏览器不得读取原始文件、canonical 事实、Metric Value 或 Analysis 持久化接口，也不得重新计算指标、Driver、Finding 资格和排名。
- 原因：让首个用户界面继承 Phase 1–5 的数字一致性、版本身份和不可变保证。

## D035 Phase 6 Dashboard 桌面信息结构

- 状态：有效
- 决定：桌面端采用深色工作流侧栏、八指标、趋势/经营利润桥/Findings 三栏分析带、产品表/客户群×产品毛利矩阵双栏明细带；页面只保留一个 `h1`。
- 响应式：窄桌面允许 Findings 跨栏、明细转单栏；移动端作为可读复核界面，不以牺牲桌面信息密度为代价。
- 可访问性：滚动表格区域必须可键盘聚焦，表格、矩阵和状态不得只依赖颜色传达含义。

## D036 Investigation 身份交接边界

- 状态：有效
- 决定：Phase 6 的每个 Finding 跳转必须保留 `finding_id`、`batch_id`、`metric_snapshot_id` 和 `analysis_run_id`，并先由不可变身份回执页确认上下文。
- 当前边界：Phase 6 不实现证据下钻和评审；Phase 7 在该身份之上建设 Evidence-first Investigation，不得静默切换批次、快照或运行。

## D037 Investigation 审批资格与审计边界

- 状态：有效
- 决定：Finding 状态机为 candidate → in_review（提交）→ approved（签发，需全部证据 verified 且结论四要素完整）/ rejected，in_review 可退回 candidate，approved 可退回 in_review；rejected 在 V1 为终态。
- 证据决策：pending/verified/rejected 之间按受控迁移，每次证据决策与 Finding 迁移都追加 ReviewEvent（含 evidence_verified/evidence_rejected，迁移 0008），审计记录只增不改。
- 边界：记录级表格只展示 canonical 数值与文件/工作表/行血缘，不在 Investigation 中重算任何分析金额；演示种子 `--fresh-batch` 通过新建批次保证门禁可重复，不改动已发布历史。

## D038 Pilot Readiness 推进顺序

- 状态：有效；用户于 2026-09-02 明确批准。
- 决定：Phase 1–10 功能窄切片之后，严格按照“仓库与验收基线修复 → 补齐 Excel 导入和报告下载的用户闭环 → 最小安全部署 → 脱敏真实数据试点 → 用试点证据决定 V1.1”推进。

## D039 产品定位：准确性优先的财务分析（经营分析列为未来扩展）

- 状态：有效；用户于 2026-09-02 明确提出并确认（讨论记录见 `01_conversations/readable/2026-09-02-positioning-accurate-financial-analysis.md`）。
- 决定：当前早期阶段，FLOW 聚焦**财务数据的收集与基于客观财务数据的客观财务分析**这一确定性任务；系统不替用户形成主观业务判断，只为其提供可追溯、可复核的落点。经营分析能力（依赖经营侧数据与业务假设的主观归因，维度与财务分析不同）是明确的**未来扩展方向**，不进入当前范围。
- 边界界定：客观上报的经营量数据（订单量、单价、履约成本等）参与的确定性归因（收入 V/P/M、履约成本 R/V/E 等）属于"客观财务分析"范畴，全部保留；分析判断由 Finance BP 作出，系统保证判断所依赖的每一个数字可复算、有出处。
- 含义：确定性引擎、对账不变量、证据与复核体系是核心资产，对应 V1 已交付能力；经营判断结构化、行业基准、作业级经营明细接入、Management Memory 学习回路移出当前路线，列为远期方向。本决策为 D038 的试点与 V1.1 决策提供内容边界：试点检验的重点是"准确性承诺"是否在真实数据上成立。
- 原因：准确性是财务工具的准入门槛，也是当前 AI 分析工具的最大失分点；财务人员对数字错误零容忍。经营分析的开放性（业务假设驱动）与早期阶段的确定性定位不同，待准确性壁垒建立后再扩展。
- 外部参照：用户于 2026-09-04 提供公众号文章《经营分析和财务分析的区别》（接地气的陈老师，2026-09-03），其七维对照（结果性 vs 过程性、科目颗粒度 vs 业务单元颗粒度、判断结论 vs 行动闭环）与本文划界互相印证；已归档 `02_research/original/06_经营分析和财务分析的区别_资料.md`。

## D040 会计基础数据与财务分析指标库立项

- 状态：有效；用户于 2026-09-05 逐项确认（调研归档见 `02_research/original/07–09`，设计草案见 `02_research/synthesis/会计与财务指标知识库_设计草案.md`）。
- 决定：在 D039「准确性优先的财务分析」定位下，新建两样基础能力——会计基础数据（会计准则 / 会计科目 / 会计分录）与财务分析指标库（数据字典 + 指标计算与勾稽关系）；系统必须可查询、可更改、可观测、可使用。
- 逐项确认：
  1. 会计基础数据做**查阅级 + 取数映射**（科目/分录/准则知识 + 科目到指标取数的映射），不做核算级总账；核算级留待脱敏试点证据；
  2. 准则覆盖面为 **CAS + IFRS 对照**（IFRS 至少覆盖 MPM 管理层业绩指标等关键概念与口径对照）；
  3. 指标库初始规模为**通用 40 指标 + 物流行业 15 指标**，宁精勿滥；
  4. 指标库建成后，`flow.metrics.logistics.v1` **迁移为库内的行业指标集版本**，保持全系统单一口径来源；
  5. 推进节奏：与 Pilot Phase 2 安全部署及脱敏真实数据试点**并行**。
- 边界：本立项不修改任何已冻结契约；不绕过 D016（AI 不创造数字）、D028/D033（不可变快照消费边界）、D031（确定性分析输出）、D037（审批资格）。指标库的变更采用版本化（新口径版本 + 旧版本保留），与已发布快照不可变原则一致。
- 后续：依据设计草案编写正式规格与实施计划，经用户批准后进入实施。

## D041 四表一注标准输出与真实财报反向解析验证

- 状态：有效；用户于 2026-09-05 在 D040 基础上补充提出（两条要求，同日确认纳入）。
- 决定：
  1. **分析标准**：财务分析基于客观财务视角，依据会计法规和会计准则；系统以标准「四表一注」（资产负债表、利润表、现金流量表、所有者权益变动表 + 附注）为基准输出物，指标分析建立在报表项目取数之上。对象模型相应新增「报表项目（StatementLineItem）」，取数链补全为「业务 → 分录 → 科目 → 报表项目 → 指标」；附注本期定位为披露项目清单 + 取数标注，不做全文生成；
  2. **验证方式**：开展真实财报反向解析验证实验——选取典型互联网公司/物流公司的当年度与当季度财报导入系统，系统据此重建「四表一注」并生成完整财经分析报告，再与公司已发布财报逐项比对，以比对结果作为准确性承诺的验证证据；差异分级为口径差异 / 解析误差 / 披露缺失，全部留痕归档。
- 边界：实验仅使用公司公开发布的财报；本实验是验证手段，不替代 Pilot Phase 2 脱敏真实数据试点，两者证据合并后优先决定 V1.1 范围；不改变任何已冻结契约与 D016/D028/D031/D033/D037 边界。
- 落地：正式规格 `docs/superpowers/specs/2026-09-05-flow-metric-dictionary-design.md` 第 1、3.6、8、10 节；实施排入 P3（报表项目落库）与 P5（验证实验）。

## D045 双轨产品结构：财务分析轨 + 经营分析轨

- 状态：有效；用户于 2026-09-06 确认（「现在要设计落地双轨架构，并按照这个来修改整个系统和项目」）。
- 决定：系统是**一套底座、两条轨道、两类受众**：
  1. **财务分析轨**（面向 Finance BP）：现有驾驶舱、Investigation、报告中心、报表分析（四表一注）、指标库，是当前建设主体；
  2. **经营分析轨**（面向经营/业务管理者）：与财务轨共享数据接入、标准数据中间层、指标语义与确定性引擎、证据/复核机制和界面体系，**区别仅在数据定义**（经营侧指标目录、数据契约与分析策略按轨道版本化扩展）；
  3. 两轨数字同源：同一指标快照身份链，不允许两套口径各自计算。
- 推进顺序（用户同日确认）：(a) 短期优先把财务分析轨全部功能与报告做完；(b) 经营分析轨不放弃既有积累，先在双轨架构下做小 demo；(c) 已有可用功能在双轨架构下同步归位。
- 取代与修订：
  - **D010 的单角色限定被取代**：恢复双受众，但以「双工作区」而非简单双角色页面实现；
  - **D039 的范围限定被修订**：经营分析从「未来扩展」变为并行第二轨；D039 的核心约束（准确性优先、确定性引擎、事实/判断/假设分离、AI 不创造数字）继续适用于两条轨道；经营分析轨的主观归因内容在未有证据治理前不得进入正式输出。
- 边界：双轨不引入新的计算引擎、不复制数据中间层；经营分析轨 demo 只读消费已发布快照，不产生新的 Finding/报告资格。

## D046 双轨执行计划（三步骤）

- 状态：有效；用户于 2026-09-06 确认（A+C 组合方案）。
