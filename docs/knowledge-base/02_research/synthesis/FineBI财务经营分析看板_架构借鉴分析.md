## 2. 一句话判断

这套看板最值得借鉴的不是某一种图表，而是一个三层分析骨架：

```text
经营问题专题
→ 财务结果、目标差距和趋势
→ 产品/客户/区域/渠道/组织等结构切片
→ 价格/数量/结构/成本/费用等数学或业务驱动
→ 明细记录
```

它把传统 Excel 中分散的收入表、成本表、费用表和预算表，组织成可复用的“问题—指标—维度—驱动—明细”路径。其优势是发现和定位较快；其不足是传统 BI 通常以看板展示为终点，未天然解决 FLOW 更重视的来源、口径版本、计算轨迹、证据复核和冻结发布。

## 3. 内容组成架构

### 3.1 第一层：以经营问题划分专题，而不是按数据表划分

公开材料反复围绕六个问题组织内容：

| 专题 | 首要问题 | 结果指标 | 继续追问 |
| --- | --- | --- | --- |
| 收入 | 增长从哪里来，质量是否健康 | 收入、增长率、预算完成率 | 产品/客户/区域/渠道贡献；是否转化为毛利和现金 |
| 成本 | 成本为什么上升 | 总成本、单位成本、成本率、预算差 | 采购价格、用量、产品结构、效率、供应商或环节 |
| 利润 | 利润在哪里形成、为何变化 | 毛利、毛利率、经营利润、净利润 | 收入、价格、数量、结构、单位成本和费用贡献 |
| 预算执行 | 目标是否达成、偏差在哪里 | 实际、预算、差额、完成率 | 期间、组织、项目、科目和责任单元 |
| 费用 | 费用增长是否合理 | 费用额、费用率、预算差 | 费用结构、投入对象、收入/毛利/客户增量回报 |
| 经营效率 | 资源是否有效转化为产出 | 周转、人效、产能/设备利用、回款周期等 | 哪个组织、产品、流程或资源形成低效 |

这一分类比“利润表、费用表、预算表”更接近用户任务，因为页面标题直接对应管理者会问的问题。但它仍需受数据可得性约束：公开财报可以支持结构、趋势、比率和部分周转分析，通常不能支持客户、订单、供应商、渠道或内部预算的细粒度下钻。

### 3.2 第二层：每个专题共享一套分析语法

成熟看板通常不是为每个专题重新发明交互，而是重复使用以下版式：

1. **范围栏**：期间、组织、区域、产品、客户或项目等全局筛选；
2. **KPI 结果卡**：本期值，同时给出预算差、同比、环比或累计完成；
3. **趋势区**：月/季/年趋势，用于识别拐点和持续性；
4. **结构区**：占比、排名、矩阵或分组表，用于找出贡献与风险集中点；
5. **差异/驱动区**：瀑布、桥或标准与实际差异，用于解释变化量；
6. **明细区**：从图形下钻到客户、产品、订单、费用项或其他记录；
7. **预警表达**：阈值色、异常高亮或排名，把注意力导向偏差最大的单元。

这形成了稳定的阅读顺序：先看结果，再判断变化，再看结构，最后定位驱动和明细。它比把所有图表铺在一屏更重要。

### 3.3 第三层：三套底层分析模型

#### 利润形成模型

公开材料采用逐层扣减关系：收入 → 毛利 → 经营利润 → 净利润。收入代表规模，毛利代表收入转化质量，费用代表资源投入，最终汇总到利润。适合使用利润瀑布、收入/成本对照、费用率和多期趋势。

#### 结构分析模型

总量沿产品、客户、区域、渠道、组织等维度切开，同时观察收入占比、毛利贡献、增长、回款和资金占用。其核心不是简单排名，而是交叉判断“规模大是否也有利润、增长是否也带来现金”。

#### 驱动因素模型

收入变化进一步拆为数量、价格和结构；利润变化进一步吸收收入、产品结构、单位成本和费用影响。驱动层的价值在于把“下降了多少”转成“哪些可计算因素贡献了多少”。但公开材料也混合了数学驱动与业务原因，FLOW 必须比模板更严格地区分两者。

## 4. 指标与维度架构

### 4.1 指标不是平铺清单，而应组成关系链

可还原出的主链为：

```text
业务规模（客户/订单/销量）
→ 收入（数量 × 价格 × 结构）
→ 毛利（收入 − 直接成本）
→ 经营利润（毛利 − 期间费用）
→ 利润质量（应收、库存、经营现金流）
→ 经营效率（周转、人效、资源利用）
```

同一指标还应配四类镜头：当前值、比较值、结构贡献、驱动贡献。比如“收入”不是一张卡，而是本期收入 + 预算/同比差 + 产品/客户贡献 + 价格/数量/结构桥。

### 4.2 维度应分为四类

| 维度类型 | 示例 | 主要用途 |
| --- | --- | --- |
| 范围维度 | 主体、合并范围、期间、币种、实际/预算版本 | 确定数字身份，不能只作为界面筛选 |
| 责任维度 | 集团、事业部、经营单元、成本中心、项目 | 预算归责与管理下钻 |
| 市场维度 | 产品、客户、区域、渠道、业务类型 | 收入与盈利结构分析 |
| 作业维度 | 订单、供应商、物料、工序、仓库、线路 | 成本与效率原因定位 |

FineBI 的典型优势是让用户动态切换这些维度；FLOW 需要额外保证不同维度的粒度、可聚合性、权限和对账总计，不允许仅因为界面能拖拽就认为组合在语义上有效。

## 5. 下钻逻辑：两个方向必须分开

### 5.1 层级下钻

这是传统 OLAP 的强项，例如：

- 时间：年 → 季 → 月 → 日；
- 组织：集团 → 事业部 → 经营单元 → 成本中心；
- 区域：大区 → 省 → 市 → 网点；
- 产品：产品线 → 产品 → SKU；
- 客户：客户群 → 客户 → 合同/订单。

FineBI 官方文档确认其支持钻取、跨表钻取、联动、跳转和过滤。这个方向回答“问题发生在哪个切片”。

### 5.2 因果/驱动下钻

这是财务分析产品更关键的方向，例如：

```text
利润下降
→ 收入 / 成本 / 费用
→ 数量 / 价格 / 结构 / 单位成本 / 费用项
→ 产品 / 客户 / 区域 / 组织
→ 记录与来源证据
```

这个方向回答“哪个数学因素贡献了变化”。传统 BI 容易把层级下钻误当成原因解释；FLOW 应要求每一级都声明关系类型：公式依赖、数学贡献、统计关联、业务假设或已核验证据，不能混称“原因”。

## 6. 对 FLOW 最值得吸收的部分

### 6.1 可直接吸收，不改变现有底层架构

1. **用问题域组织导航。** 在“报表/指标”之外增加收入质量、利润变化、成本压力、费用效率、现金安全等问题入口；底层仍引用同一事实与指标版本。
2. **统一专题页语法。** 所有专题遵循“结果卡 → 趋势 → 结构 → 驱动 → 明细/证据”，降低学习成本，也方便报告章节复用。
3. **把实际、预算、差异、完成率作为一个指标视图。** 不把预算看板做成孤立模块；预算是收入、成本、利润、费用各专题的比较场景。
4. **把增长质量做成交叉判断。** 收入应与毛利、应收和现金联动；客户或产品价值不能只按收入排名。
5. **同时支持层级下钻与驱动下钻。** 前者定位业务切片，后者解释变化量，最终都进入 FLOW 的证据页。
6. **用专题模板而非固定大屏。** 页面骨架可复用，指标与可用维度由数据契约和适用性规则决定；缺失时显式降级。

这些都与 FLOW 已有“总览 + 异常 + 专题下钻”、Metric Snapshot、Driver Contribution 和 Evidence-first Investigation 一致，属于对现有方向的强化，不需要新建第二套计算引擎。

### 6.2 值得借鉴，但必须按 FLOW 原则改造

| FineBI 常见做法 | FLOW 改造要求 |
| --- | --- |
| 用户在组件内配置计算指标 | 正式数字必须来自版本化指标定义与服务端确定性计算；展示层不另建财务公式 |
| 图表直接下钻到多表字段 | 先校验事实粒度、关联基数、聚合规则、权限和总计对账 |
| 用红黄绿阈值表达异常 | 阈值必须有来源、适用范围和版本；无权威依据时只显示偏差，不贴“健康/危险”标签 |
| 价格、效率、供应商等被直接称为原因 | 数学驱动与业务因果分开；业务原因需要外部证据或人工判断 |
| 实时/日度被当作普遍优势 | 刷新频率由源系统与管理节奏决定；公开财报和月结数据不伪装实时 |
| 自助拖拽形成任意分析 | 允许探索，但正式发布只能消费已验证、可追溯的快照 |

### 6.3 不建议照搬

1. **把看板当最终产品。** FLOW 的价值链应继续覆盖导入、质量、计算、复核、发布，而不是止于可视化。
2. **一屏堆满所有指标。** 信息密度服务于决策链，不服务于图表数量；专题页比“大而全总屏”更有效。
3. **把通用模板指标当企业口径。** 预算、费用、效率高度依赖企业责任中心和业务模式，必须在内部数据试点验证。
4. **展示层自由重算。** 这会破坏 D049 的口径、计算、追溯和独立验证链。
5. **用营销性预测或 AI 结论补数据缺口。** 公开数据没有客户、订单或预算细项时，应明确“不支持该下钻”。

## 7. 与当前 FLOW 计划的映射建议

这份参考不应打断当前 C03“期间、范围、精度与异常语义”的执行，也不应提前把经营轨主观分析塞入公开财报版本。建议按阶段吸收：

| FLOW 工作包 | 可吸收内容 | 边界 |
| --- | --- | --- |
| C03–C06 指标治理 | 指标的比较镜头、适用维度、阈值来源、依赖关系和使用方 | 不把界面自定义公式变成正式口径 |
| D01 客观分析目录 | 用“收入/利润/成本/费用/现金/效率”作为问题分类；为每类定义趋势、结构、比率和可算分解 | 公开披露不足时拒绝客户/订单/PVM 等分析 |
| D02 图表投影 | 统一“结果—趋势—结构—驱动”的服务端投影契约 | 每个图点保留事实与定义身份 |
| D05 复核资格 | 驱动点击进入来源、公式、适用性和复核状态 | 不把统计关联自动升级为原因 |
| E01–E05 用户流程与报告 | 驾驶舱专题与报告章节共享同一分析快照和问题结构 | 报告只纳入已批准客观结论 |
| G01–G03 内部数据试点 | 验证预算执行、费用效率、客户/产品盈利和作业效率维度 | 合成数据只验证接口，不宣称真实业务价值 |

## 8. 建议补充的产品元数据

为了把“成熟看板的组织能力”吸收到 FLOW，而不复制传统 BI 的脆弱性，可以在后续设计中为每个分析专题明确以下元数据：

```text
AnalysisTopic
- question_id / question_text          这页回答什么问题
- audience / cadence                   谁在什么节奏使用
- primary_metrics                      首要结果指标
- comparison_modes                     预算、同比、环比、YTD 等
- allowed_dimensions                   允许的维度与层级
- driver_methods                       可用数学分解及适用条件
- cross_metric_checks                  收入—利润—现金等质量联查
- detail_grain                         最深可到什么记录粒度
- evidence_requirements                来源与复核要求
- degradation_reason                   数据不足时为何降级
- report_section                       对应报告章节
```

这不是建议立即新增数据库表，而是建议 D01/D02 设计时把这些字段当作契约检查清单。

## 9. 最终结论

FineBI 参考验证了 FLOW 已经选对的三件事：指标必须与维度结合、总览必须通向专题下钻、结果必须继续拆到驱动。它最能补强 FLOW 的地方，是把“收入、成本、利润、预算、费用、效率”统一组织成问题导向的专题模板，并让预算和多维切片贯穿所有专题，而不是独立报表。

FLOW 不应复制的，是把灵活拖拽、图表联动或一套模板本身当作可信分析。FLOW 的差异化仍应放在五条链：来源、口径、计算、追溯、验证；以及把每一次下钻最终接到公式、数据粒度、源记录、证据和复核状态。换句话说，FineBI 可以借鉴“怎么看”，FLOW 要继续解决“为什么这个数字可信、这个解释能否发布”。
