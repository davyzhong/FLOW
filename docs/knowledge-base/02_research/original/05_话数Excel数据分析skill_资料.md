## 一、为什么做这个 skill（原文开头）

作者离开美团前的一段经历：作为新用户运营负责人，每天需提前 2 小时取数、分析，在早会上解释昨天数据为什么波动、据此调整当天策略。"短周期数据归因其实挺无聊的，但没办法，必须做"——数据变化可能与天气、运营动作、竞争对手策略、周中周末有关，每天都要在一堆因素里给出说得过去的解释。因此把对 agent 能力的理解 + 以前做运营的数据处理分析经验做成了这个 skill，正式开源（MIT 协议）。

## 二、它能帮你干嘛（用户怎么说）

丢一份 Excel 或 CSV，说人话即可：

| 用户说法 | 系统行为 |
|---|---|
| 「帮我分析下这份销售表」 | 走完整个流程，最后交一份报告 |
| 「这两个数怎么对不上」 | **先查口径差异，而不是先查算错**（对不上十次有八次是两边分母不一样） |
| 「这个数靠谱吗」 | 对账加独立复核，告诉你哪一条最脆弱 |
| 「帮我把这份表洗干净」 | 洗完附一份**可回放的清洗脚本**，每一步影响了多少行都有记录 |
| 「这个数你怎么算出来的」 | 口径回溯 |

**八步工作流**：`体检 → 清洗 → 对齐 → 分析 → 对账 → 交付 → 验图 → 质控`。按需执行：查一个数就直接查，要报告才全走。

### 三个最值得说的环节（原文重点）

**第 1 步·体检**：大部分工具 `pd.read_excel()` 读进来的那一刻，合并单元格、单元格格式、原始类型就全丢了，之后所有判断都建立在损毁的信息上。作者实测一份典型的中国式销售表（标题占两行、两级表头、中间夹着"华东小计"、尾巴三行是合计），用"找对表头+清掉千分位"这种看着挺周全的做法去算月度总额，**比真值高出 161%，零报错、零警告**。所以这个 skill 先用 **openpyxl 读原始单元格**做体检：表头在哪、哪几行混着标题和小计、哪些列有猫腻全列出来，然后才开始算。

**第 5 步·对账**：表里的"合计"行，几乎所有工具都当噪音过滤掉，但那其实是原表作者用公式算出来的真值，等于**免费的校验和**。skill 会拿清洗后的明细自己求和，去对表里自带的合计——测试时它揪出过一个差 10 块钱的错（表内小计写 6,490,430，明细算出来 6,490,420，相对误差 0.00%，肉眼永远发现不了，是造表的人手填小计时填错的）。

**第 8 步·质控**：数字全对账、退出码全绿，结论仍然可能是错的——因为分析窗口是你自己挑的，你看它的时候带着它应该成立的先验。所以最后一步是**另派一个没参与创作的 agent，从原始数据重算一遍，专门来拆台**：这个时间段是不是挑出来的？外部基准的分母对得上吗？"已剔除某某偏差"这类话，代码里真做到了吗？

### 报告输出格式（4 种）

1. **HTML 网页报告**：自包含、不联网、图表用内联 SVG 手画，发微信当附件都能直接打开；
2. **Excel**：图表是原生的，引用数据 sheet，改个数图跟着变；
3. **Word**：走 Amazon six-pager 那套叙述体，不用项目符号；
4. **PPT**：转交给作者另一个 skill `huashu-design` 去做（"术业有专攻"）。

## 三、压测验证（10 份真实公开数据）

发布前找了**十份真实的公开业务数据**做压测，每份单独派一个独立 agent 实跑全流程。强调真实：Kaggle 上那类 HR、营销练手数据集大多是合成的，合成数据没有真实的脏。任务里不提示任何坑——坑是数据本身就有的。范围：销售、人力、财务、运营、宏观、财报，从 106 万行的电商交易明细到 21 万行的纽约市政预算。

### 压测案例 1：纽约市 311 住房工单（159,275 条，2026 Q2 全量）——images/05_3.png

任务：站在运营负责人角度做季度复盘。首屏亮点：
- 月报口径里处理时长在涨，看起来是效率下降要加强管理；往下拆一层发现是**品类结构变了**：处理最快的暖气类工单随供暖季结束大量消失，把整体中位数抬了上去；同口径再看，13 个品类里 12 个在变快——**教科书里的辛普森悖论，它自己撞见、自己拆对了**。
- 右边关键数字：**32.4% 的工单是以"没能进门"结案的**，官方口径全算达成；所以达成率是 86.5% 还是 49.5%，取决于认哪个口径——**它把两个口径都摆出来，让读者自己选**。

### 压测案例 2：106 万行英国电商交易明细（销售 VP 业绩复盘）——images/05_4.png

- 首屏标题直接把结论写在脸上：**"表面的营收增长是新品补出来的"**——两年都在卖的 3,145 个老 SKU 营收掉了 12.9%，651 个新品带来 £2.05M 把窟窿填上，而同期英国线上大盘还在两位数扩张。
- 导语顺势把明年预算的问题从"投国内还是投海外"改写成"先止血还是先扩张"——**从"发生了什么"推到"所以该做什么"**。
- 数据里有一万多个转不成数字的发票号，它没有静默丢掉，逐个去看：查出 C 开头的是取消单、A 开头的是坏账调整，甚至从商品代码里摸出了这家公司上线 Amazon 渠道的时点——**一万多个脏值最后一个个都成了业务线索**。

### 压测案例 3：纽约市 21 万行市政预算（"多出来的109亿怎么解释"）——images/05_5.png

- 结论："**这109亿不是超支，是记账时点**"。
- 首屏小字（作者最喜欢的一行）：**"对账21/21项，与预算办公室印刷卷分毫不差"**。
- 这个分毫不差来之不易：第一版它算出过一个行数守恒、金额恒等、内部校验全绿的数字，拿去对外部权威数字，**错了整整一个财年**——因为那份数据的列名和字面意思对不上（fiscal_year=2026 那行的"采纳预算"列，装的其实是 FY2025 的数）。
- 教训：**内部校验全对的报告，可以整体错一个财年，而且没有任何内部检查能发现——是"必须查外部基准"这条规则把它救回来的。**

### 压测案例 4：28,225 份真实薪酬调查问卷（HR 薪酬公平诊断）——images/05_6.png

- 数据脏得很有代表性：11 种货币混在同一列，行业随手填出了 1,228 种写法，最高年薪 1.02 亿美元。
- 它把那个 1.02 亿**当录入错误处理了，没当发现**（Twyman's Law：看起来异常的数字通常是错的，先当 bug 查，排除了才当发现）。
- 28,225 份问卷进入分析的是其中 22,918 份美元样本；结论自带证明边界：**"能证明差距随工龄扩大，证明不了起点为零"**——这个区别直接写在首屏。

四份报告都是独立 agent 自己跑出来的，另派复核 agent 从原始数据把核心数字重算了一遍，正文里引的都是复核对上的那些。

## 四、skill 的设计逻辑（方法论精华）

1. **核心缺陷认知**：AI 算错的时候不会报错。写代码错了会抛异常；做数据分析错了什么都不会发生，**一个错误的数字和正确的数字交付出去的时候长得完全一样**。整套流程里的对账、验图、独立质控，都是在给这个不存在的报错机制补位。
2. **角色激发**（灵感来自 Anthropic 的 AI 心理学研究）：skill 第一句话是"如果世界上最好的数据分析能力可以被装进一个文件，那就是你"，然后要求它依次成为领域专家、数据分析师、战略顾问、视觉设计师、前端工程师、质控，像一个百万美元项目组那样工作。模型的表现和它被引导进入的角色状态强相关——"认定自己是一个会用pandas的助手，产出就真的止步于助手"。
3. **Test-time scaling 式流程约束**：八步流程本质是强制模型多想。每跑完一个脚本，要回答"看到了什么、意味着什么、下一步查什么"才准往下走。skill 里有条判据：**"如果跑完脚本之后，你的下一步动作和跑之前计划的一模一样，说明你没有真的在看那个输出。"**
4. **脚本的定位**：skill 内置一堆脚本（体检、清洗、陷阱扫描、对账、验图、验Word），但定位写得很清楚：**它们是眼睛，不是大脑；是地板，不是天花板**。遇到脚本处理不了的结构，agent 该自己写代码、自己判断。
5. **统计与图表规范**（每条防的都是"图没错但在误导人"）：
   - 默认给**中位数和五数概括**，均值只当陪衬——业务数据几乎总是右偏的（Tukey 抗差统计）；
   - 类别超过 3 个**直接拒绝画饼图**——人眼读角度和面积的精度远低于读长度（1984 年感知实验）；
   - 柱形图数值轴**强制从 0 开始**；**双轴图整个禁掉**；不完整的最后一个周期画虚线。
6. **图表类型按数据需要选**（全部 agent 手写内联 SVG，不用图表库，所以报告离线单开就能看）：
   - **洛伦兹曲线**（images/05_7.png）：回答"营收有多集中"，弧线离对角虚线越远越集中；
   - **双峰分布柱状图**（images/05_8.png）：认出零售和批发两群客户混在同一份账本里，阈值骑墙的那根柱子单独标灰，不硬分给任何一侧；
   - **事件研究图**（images/05_9.png）：验证涨价是不是增值税调整导致的，把生效日画进图里，发现价格抬升发生在生效日之前；
   - **价量分解**（images/05_10.png）：把营收变化拆成价格效应、数量效应和 SKU 进出，各自贡献一目了然；
   - **哑铃图**（images/05_11.png）：四条线里一眼看出预算修订几乎全落在非人力支出；
   - **小倍数图**（images/05_12.png）：每个品类一格共享同一把尺子，比把 13 条线塞进一张图清楚一个数量级，连怎么读都替读者写好了。

## 五、部署与兼容

- **不挑 agent**：Claude Code、Codex、WorkBuddy、豆包、DeepSeek Harness 都可以。
- **环境自适应**：开工时先探测所处环境——能跑 Python 就跑脚本；能派子任务就并行分析；连脚本都跑不了的环境，转成直接告诉你在 Excel 里怎么点、公式怎么写。
- **依赖极轻**：核心流程只依赖一个 openpyxl；处理 CSV 连这个都不需要（纯标准库）；验图那一步装了 playwright 会更全，缺了它会明说，不会假装验过。
- **安装**：`npx skills add alchaincyf/huashu-excel`，或 clone 到 agent 读 skill 的目录；最简单的方式——把仓库链接丢给 agent，说"读一下这个仓库的 SKILL.md，然后帮我分析这份表"。

## 七、对我们项目的直接启示

1. **可以直接作为我们产品的"数据分析引擎"候选**：MIT 开源、无重依赖、面向 agent 设计——我们的财务驾驶舱后台可以用它做 Excel 数据体检与挖掘层，也可以借鉴其思路自研。
2. **"AI 算错不报错"是本类产品的第一性问题**，解决方案三板斧：表内对账（合计行当校验和）+ 外部基准对账 + 独立 agent 质控。财务场景天然有大量"合计行""勾稽关系""外部基准（税局/审计口径）"，这套方法在财务领域会比电商场景更有效。
3. **报告即产品**：四种输出（HTML/Excel/Word/PPT）+ 结论式首屏 + 证明边界写法，与资料二/三的 PPT 范式完全同构——报告生成器可以把"结论句模板 + 证据图 + 口径边界"做成标准化能力。
4. **图表规范可直接抄**：中位数优先、>3 类不画饼图、柱形图零基线、禁双轴、不完整周期画虚线——写成我们指标系统的"图表渲染约束"。
