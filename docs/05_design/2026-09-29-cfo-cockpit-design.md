# 财务总监驾驶舱——详细设计与原型

> 用户裁决（2026-09-29）：以数据熊《集团财务总监经营驾驶舱》为原型参照（功能与界面
> 大幅度借鉴），同时调研市面竞品是否有更专业选择；本轮只做文档与设计（含原型），
> 不动手开发。设计中的开放问题用苏格拉底提问法与用户逐项确认。
>
> 本文是设计输入与原型规格，不是实施计划；任何落地须先入 CURRENT_ROADMAP 领取任务。

## 1. 原型参照是什么

数据熊《集团财务总监经营驾驶舱》（宋岳清出品）已完整归档：
[01 号资料逐页记录](../knowledge-base/02_research/original/01_集团财务总监驾驶舱_资料.md)
（11 张配图 `original/images/01_1.png ~ 01_11.png`），另有 Power BI 成熟版的七项借鉴
分析（挂 U3/U6/U7）。一句话概括该原型：

- **面向集团型企业**的财务分析工具，数据入口是中国四表标准 Excel/CSV
  （字段映射 + 勾稽校验 + 指标计算 + 集团合并）；
- **十大模块**：集团总览 / 利润增长 / 盈利能力 / 费用分析 / 资产负债 /
  营运资金 / 现金流 / 财务风险 / 集团合并 / 数据中心；
- **全局筛选**：期间、组织口径（合并/管理汇总/单体）、币种、累计/当月；
- **每页固定骨架**：KPI 卡行（每卡双基准：同比 + 较预算）→ 2~3 大图表 →
  2~3 明细/行动表 → 底部「经营结论」判断句横条；
- **「问题—原因—措施—跟踪」闭环**：预警清单（带等级）→ 管理层关注
  （带负责人与期限）→ 应对措施，跨页呼应。

原型对标价值 ⭐⭐⭐⭐⭐：它把「值必带比较基准」「口径随图附」「守恒瀑布」
「事实与建议分离」「数据→结论→行动」做成了完整可照抄的界面范式——与 FLOW
D01 事实合同、口径标注、守恒桥、Finding 四要素**天然同频**。

## 2. FLOW 驾驶舱的定位与边界

**FLOW 驾驶舱 = D052「企业内部分析工作台」的高管呈现层**，不是独立产品，
更不是原型的单机 HTML 文件形态：

| 维度 | 数据熊原型 | FLOW 驾驶舱（本设计） |
|---|---|---|
| 形态 | 单文件离线 HTML，数据存本机 | B/S 系统（Next.js + FastAPI + PostgreSQL），AppShell 内页面 |
| 数据入口 | 手工导入中国四表 Excel | 研发期：公开财报管线（阿里/菜鸟等公开数据）；内部期：L2 内部/预算层导入走同一导入通道 |
| 指标口径 | 看板内写死 | 治理化指标字典（v1.2，65 指标 + 16 行业参考包），口径是一等公民 |
| 结论条 | 模板句 | 必须由 Findings/快照机器生成并可溯源（AI 不创造数字） |
| 双基准 | 同比 + 较预算 | 同比可先行（公开数据有）；预算/目标基准属 L2 内部层，内部期启用 |
| 集团合并 | 管理汇总/抵销/单体 | 结构复用，数据待内部期；公开期以单主体 + 分部视角呈现 |
| 治理层 | 无 | 冻结发布、证据链、SHA 溯源、口径版本、独立验证（FLOW 已有且更严格） |

D001（产品不是单一驾驶舱）不变：驾驶舱是分析工作台的**一屏式入口**，
下钻仍进入现有各分析页（报表分析、指标库、归因、问数、报告）。

## 3. 竞品调研结论（是否有更专业的选择）

已有竞品档案：C01–C20 素材库（vault 侧）、FineBI 三层模型借鉴分析（2026-09-06）、
开源 BI 评估（2026-09-09）、数据熊 Power BI 版评估（2026-09-09）；本轮补充
2026-09 市场面调研。四类玩家结论：

| 阵营 | 代表 | 强项 | 对 FLOW 的结论 |
|---|---|---|---|
| 国产 BI 平台 | 帆软 FineReport/FineBI、Smartbi、观远、永洪 | 1000+ 行业模板、拖拽自助、中国式报表、实时大数据 | 展示能力强但**以看板为终点**，无口径治理/冻结/审计；模板范式可借鉴（FineBI「问题→指标→维度→驱动→明细」三层骨架已入库） |
| ERP 原厂 | 用友 BIP、金蝶苍穹/EAS、SAP SAC、Oracle EPM | 紧贴 ERP 与合并，账务一体化 | 绑定自家 ERP、实施重；ERP 内置 BI 常被业务弃用回归 Excel（公开报道），不构成方向威胁 |
| EPM/FP&A | Anaplan、Pigment、Workday Adaptive、OneStream、Planful、Vena、Jedox | 计划/预算/预测/合并建模强，CFO 人群对齐 | 面向「计划编制」而非「分析呈现」，价格与实施门槛高；其 13 周滚动预测、滚动预算思想登记为内部期功能参照 |
| 专业模板/单机 | 数据熊系列（本原型） | 财务教科书式指标体系 + 管理闭环，开箱即用 | **原型主参照**；单机形态与无治理是 FLOW 的差异化空间 |

**裁决建议**：没有发现「更专业且更合适」的整体替代——数据熊原型在**界面范式与
指标体系**上仍是最佳底版；FLOW 的差异化在它没有的**治理层 + AI 原生**
（检索引用型问数、结论可溯源、证据链）。借鉴组合 = 数据熊（页面骨架/模块划分/
图表选型）+ FineBI（问题驱动的专题组织）+ FLOW 既有合同（值带基准/口径附表/
守恒核对/建议状态脚注——已在 2026-09-09 评估册登记）。

## 4. 信息架构（IA）

### 4.1 全局框架

```
┌────────────────────────────────────────────────────────────────────┐
│ AppShell（左侧工作流导航，现有）                                     │
│ ┌──────────────────────────────────────────────────────────────┐  │
│ │ 顶部筛选条（驾驶舱组内常驻）：                                  │  │
│ │ [分析主体▾] [期间▾] [口径▾] [币种▾] [累计|当月]   数据更新: 时间 │  │
│ ├──────────────────────────────────────────────────────────────┤  │
│ │                                                                │  │
│ │   驾驶舱内容区（十大模块 → 驾驶舱子导航，见 4.2）               │  │
│ │                                                                │  │
│ └──────────────────────────────────────────────────────────────┘  │
└────────────────────────────────────────────────────────────────────┘
```

- 驾驶舱是 AppShell 内的**页面组**（`/cockpit/*` 路由族），子导航用
  驾驶舱内二级 tab 或侧栏分组（原型为独立左侧栏；FLOW 保留唯一
  workflow-nav，驾驶舱模块在 nav 中为一个分组入口 + 组内二级导航，
  遵守前端页面规范「组件不自带 shell」）；
- 筛选状态进 URL query（可分享/可回链），全局联动所有模块；
- 每页右上角显示数据更新时间与冻结批次链接（溯源入口）。

研发期适配说明：原型演示数据是「集团 5 单元」，FLOW 公开期默认主体为
单一公司（阿里/菜鸟等公开财报主体）。因此：

- **集团总览/合并**在公开期以「主体 + 分部」视角呈现（如菜鸟分部、
  事业部运营指标 YAML 已是 O2 现成输入）；集团合并域整体推迟到内部期；

- **账龄/13 周预测/资金安排**公开期标注「内部期功能」，不渲染假数据
  （模态五态：该数据域无来源时显式 unavailable，不是空数组）。

### 5.10 数据中心

原型的数据中心 = 导入/映射/校验/日志，FLOW 已有等价物（导入管线、
manifest、校验规则、发布冻结）。因此**不新建独立导入页面**，而是把管线健康度
作为只读状态呈现——这既是「可见专业治理」的外显，也让 CFO 在读数之前先确认数据可信。

**v1.0 原型已实现的 6 个图表 + 2 个信息块**：

| 图表 | 回答的问题 | 状态 |
|---|---|---|
| 勾稽校验通过率（按校验族） | 六类校验规则各自通过率如何？ | ✅ v1.0 新增 |
| 数据新鲜度 | 各管线环节距今多少天？哪个环节最慢？ | ✅ v1.0 新增 |
| 字段映射覆盖（源字段 → 标准字段） | 哪些字段还需人工确认？ | ✅ v1.0 新增 |
| 导入数据量分布（按报告类型） | 四表 + 附注各导入了多少行？ | ✅ v1.0 新增 |
| 数据质量雷达（六维） | 本主体 vs 行业均值，短板在哪一维？ | ✅ v1.0 新增 |
| 管线吞吐（近 12 期） | 导入量与校验通过率的历史走势？ | ✅ v1.0 新增 |
| 数据校验结果明细（表） | 逐条规则的通过状态与耗时？ | ✅ v1.0 新增（补耗时列） |
| 刷新与冻结时间线 | **谁在什么时候改了什么？** | ✅ v1.0 新增 |

**设计要点**：刷新时间线带**操作人**是安全规格 §8 审计要求的外显——CFO 需要知道
"这份数据谁在什么时候更新过"。这一条直接体现 FLOW 的「可见专业治理」原则，
是与通用 BI 的显著差异（后者只有"最后更新时间"，无操作人）。

### 10.2 待新增 Action（3 个）

现有 `Action` 枚举共 58 项（规格 §2.1）。驾驶舱需新增 3 项，全部走 §4.3「unknown action 默认拒绝」的反面——即**必须显式登记**，否则全部请求被拒：

（`finance_bp` / `analyst` / `rule_owner` / `ai_analyst` / `ai_cfo` / `service_account`）中
