# FLOW 第二代静态知识刷新与战略重基线设计

> 本设计处理两个同时发生的变化：Obsidian 内容相对首版静态知识基线显著增长；Davybase 已具备把文章正文和图片转换为结构化 Markdown 摘要的能力。目标不是恢复 FLOW 对动态 Obsidian 的日常依赖，而是完成一次可复现、可审查、可发布的新静态知识重建，并据此重新审查项目目标、产品设计与执行计划。

## 1. 决策摘要

采用“两阶段、四证据层、单一静态出口”方案：

1. 等待当前 Davybase 全库图片解读批次结束并完成失败收口；
2. 以批次结束后的首个 15:00 对应 Obsidian Git 提交作为新截面；若 15:00 时仍有知识化写入，则顺延到下一次满足稳定条件的 15:00；
3. 从旧可复现截面 `ada825ce` 增量重建来源目录、主题路由、图文摘要、知识卡片、领域手册和产品映射；
4. 按 `flow-knowledge-YYYY-MM-DD.N` 规则构建并封存 sealed candidate，但保持 `CURRENT_RELEASE` 不变；
5. 基于 sealed candidate 完成战略影响评估和用户裁决，再通过 K6 原子激活新 release、产品文档和路线图；
6. 新知识可以产生决策提案，不能静默覆盖 D052–D054 或其他正式决策。

本设计不授权直接修改产品代码，也不把图片模型输出提升为正式事实。

## 2. 当前事实与问题

### 2.1 已有基线

当前正式知识发布为 `flow-knowledge-2026-09-12.1`。其运行纪律是正确的：FLOW 日常使用仓库内静态知识，不动态追读 Obsidian；只有显式知识维护任务才能创建新截面。

旧来源基线在治理文件中已从不可复现的 `2026-09-12 15:46` 瞬时计数订正为可永久复现的 Obsidian Git 对象。规范仓库是 `git@github.com:davyzhong/ObsidianWiki.git`，完整 commit 为 `ada825ce7ed132ab8b550c3a838b3f49860123c7`，完整 tree 为 `36274b2463aad9eae069af805e53e937c704c381`。本轮所有差异均以完整 tree ID 为机器输入，短 SHA 只用于人类阅读。该基线对应：

- 微信知识库 1,630 篇；
- 财务与会计 285 篇；
- 企业管理 453 篇；
- 跨境物流 125 篇；
- wiki 财务关键词 824 篇；
- 合计声明 3,317 个来源条目。

### 2.2 当前增量和知识化能力

2026-09-17 盘点时，Obsidian 约有 16,379 篇 Markdown 和 27,878 张图片。核心四类当前数量约为：

| 分类 | 当前数量 | 相对旧可复现截面 |
|---|---:|---:|
| 企业管理 | 594 | +141 |
| 财务与会计 | 368 | +83 |
| 跨境物流 | 125 | 0 |
| 微信知识库 | 1,646 | +16 |
| 合计 | 2,733 | +240 |

Davybase 已提供两条互斥知识化路径：

- `note_summary.py`：为无图且满足条件的文档生成结构化摘要；
- `image_digest.py`：为含图微信文章生成正文摘要和逐图结构化解读。

盘点时后台图片批次仍在运行，数字会继续变化。因此任何“当前已完成篇数”都只能是运行证据，不能作为新 release 的冻结计数。

### 2.3 现有第二截面的定位

`2026-09-17-obsidian-delta-scan.md` 已完成有价值的主题快评，并登记借鉴项 #20–#24，但它不是新的静态知识 release：

1. 使用文件 birth time，而不是固定 Git tree 作为新增边界；
2. 203 篇增量数已经小于按可复现旧截面对账得到的至少 240 篇；
3. 附录增强统计发生在长批次中途；
4. 只形成研究路标，没有重建 coverage、release lock、知识卡片和产品映射；
5. 当前正式产品文档仍引用旧 release。

因此该文件保留为预扫描证据，新版本不得覆盖或伪装其历史状态；最终刷新报告应引用并订正它。

## 3. 目标与非目标

### 3.1 目标

1. 建立一个可由 Git tree、清单和哈希重复验证的新 Obsidian 固定截面；
2. 对 FLOW 相关来源实现“目录全量、语义全量、高价值精读”的分层覆盖；
3. 把正文和图片解读共同纳入检索、主题路由与候选提炼；
4. 把稳定知识重新发布为 FLOW 自有的静态卡片、手册、模式和产品映射；
5. 让其他 Agent 在没有 Obsidian 和 Davybase 的情况下，仅凭 FLOW 仓库即可正确规划和实现；
6. 基于新 release 对项目目标和计划进行一次完整影响评估，并形成明确的保留、修订、新增、删除和后置结论。

### 3.2 非目标

- 不把整个 Obsidian vault 原文复制进 FLOW；
- 不把日常任务恢复为动态读取 Obsidian；
- 不把 AI 摘要、图片转录或公众号观点当作官方准则；
- 不因知识新增自动修改正式指标、会计口径、事实合同或路线图优先级；
- 不把个人信息、户外资料或其他敏感/无关目录送入外部模型；
- 不在本轮顺便实现内部工作台、行业指标包或新的前端页面。

## 4. 新截面冻结合同

### 4.1 截面时点

新截面采用“图片批次完成后的首个稳定 15:00”：

1. Davybase 图片解读主进程已经退出；
2. 失败队列完成重试或形成显式例外清单；
3. 15:00 前后至少 30 分钟没有任何 vault writer 写入；
4. Obsidian 工作树已提交，包含 staged、unstaged 和 untracked 在内均为空；
5. 记录规范仓库 URL、完整 commit、完整 tree hash、提交时间、文件数和字节数。

时区固定为 `Asia/Shanghai`。执行者在 14:30 获取 vault 全 writer 排他锁，禁止 Davybase、Obsidian 同步、备份、人工编辑和其他任务继续写入；15:00 记录候选 HEAD/tree；15:30 验证 HEAD/tree 未变化、工作树为空、所有 writer 已退出，再把该完整 commit/tree 锚定为正式截面。任一条件失败则释放锁并顺延到下一次稳定的 15:00。不得再用 mtime、birth time 或运行中的目录计数代替 Git tree。

### 4.2 差异基线

增量一律按：

```text
旧 tree `36274b2463aad9eae069af805e53e937c704c381`
→ 截面清单中登记的新稳定 tree
```

计算新增、删除、重命名和内容变化。Davybase 写入的摘要/图片附录属于“内容增强”，不得误计为新来源。

### 4.3 截面登记

新来源基线使用独立、版本化的输入描述，不覆盖 2026-09-12 的 `source-inputs.yaml`。旧基线机器分母固定为 3,317；3,035 仅作为历史瞬时声明保留，不再参与新版本的计算。新基线至少记录：

- snapshot ID；
- vault commit 与 tree hash；
- source ID、相对路径、标题、作者、来源 URL；
- 文件 SHA-256、正文 SHA-256、图片集合 SHA-256；
- 是否包含摘要附录、图片附录及其模型版本；
- K 域、权威级别、敏感级别、可用性；
- 相对旧截面的 presence/path/body/enrichment 差异维度；
- FLOW 处置状态。

### 4.4 稳定身份与哈希算法

- 路径统一为 vault 根相对 POSIX 路径，Unicode 使用 NFC，文本换行规范化为 LF，排序按 UTF-8 字节序；
- source ID 优先使用稳定的原始 URL/外部 note ID；不存在时使用前缀 `SRC-LOCAL-v1-` 加 SHA-256 的前 20 个十六进制字符：SHA-256 输入是 UTF-8 编码的无空格、键序固定 JSON 数组 `["flow-source-id-v1", source_type, normalized_origin, author_or_empty, first_title, first_body_sha256]`。首次登记结果写入版本化 `source-id-registry.tsv`，该 registry 是后续重命名/改标题/改正文时的唯一身份权威输入，并纳入 release lock；
- `body_sha256` 在规范化文本上计算，并剥离所有 `%%davybase-image-notes-*%%` 和 `%%davybase-summary-*%%` 机器附录；
- 单图身份为规范化相对路径、文件内容 SHA-256 和正文嵌入序号；图片集合哈希按嵌入序号、路径 UTF-8 字节序稳定序列化后计算；
- 差异 universe 是新旧 allowlist source ID 的并集；每个 ID 独立记录 `presence_change`（added/deleted/present）、`path_changed`、`body_changed` 和 `enrichment_changed` 三个布尔量，允许同一来源同时发生重命名、正文变化和附录增强；路径变化仅在稳定 ID/registry 匹配时成立，不使用模糊标题阈值自动认定；
- 每个 universe 输入必须恰好进入一个 presence 状态和一个处理终态，各差异维度分别对账，重复或遗漏均使截面构建失败。

## 5. 覆盖模型

### 5.1 全库目录层

对整个 vault 在 Obsidian 本地建立只读目录和统计，不对全部 16,000 余篇进行同深度精读。目录层覆盖所有 Markdown、图片和主要附件，回答“有什么、在哪里、是否变化、能否读取”。FLOW 仓库只接收 allowlist 范围的逐项 L0；敏感和排除目录只接收聚合数量与不可逆摘要，不接收路径、标题、作者或逐文件哈希。

### 5.2 FLOW 核心业务层

核心深度范围至少包括：

- `03_财务与会计`；
- `02_企业管理`；
- `04_跨境物流`；
- `processed/微信知识库`；
- `wiki/` 中命中财务、经营、预算、成本、现金、应收、指标、分析、报告、物流和业财等主题的条目。

该层要求摘要/附录级全量路由，并对 HIGH 候选回读正文。HIGH 规则在运行前冻结，至少覆盖：与当前产品目标的直接性、可复用程度、来源质量、信息具体度、增量性和敏感风险；自动评分、人工 override 和理由均保留。MED/LOW 按知识域和来源分层双审抽样，HIGH 漏检率必须不高于 5%，否则修订路由规则并对该分层重跑。未经最小人工筛查的失败项不得被推定为非 HIGH。

### 5.3 产品与工程扩展层

为了刷新 FLOW 的产品和实施计划，定向扫描：

- 产品管理；
- AI 与编程、AI/机器学习；
- 系统架构、前端、后端、数据库和 DevOps。

该层只收集与 FLOW 产品设计、AI 可验证性、知识治理、企业权限、数据契约、分析交互和可靠性直接相关的内容，不建设通用软件工程百科。

### 5.4 知识域

保留 K1–K8，并新增两个横切域：

| 域 | 内容 |
|---|---|
| K1 | 财务报表、科目与勾稽 |
| K2 | 财务分析方法 |
| K3 | 指标、公式与口径 |
| K4 | 经营分析、归因与经营分析会 |
| K5 | 驾驶舱、图表与可视表达 |
| K6 | 预算、预测与预实差异 |
| K7 | 业财融合、主数据和多维盈利 |
| K8 | AI 财务分析与可验证 AI |
| K9 | 财务分析产品、交互与报告体验 |
| K10 | 知识治理、AI 工程、安全与运行保障 |

K9/K10 是索引扩展，不自动扩大 FLOW 产品范围。

## 6. 图片知识化合同

### 6.1 覆盖要求

1. 微信知识库中所有可解析、超过过滤阈值的正文图片完成解读或登记失败原因；
2. 财务与会计、企业管理等核心目录中的含图文档也必须纳入处理，不能只覆盖微信账号目录；
3. 装饰图、二维码、头像和重复封面可过滤，但必须记录过滤规则和数量；
4. 图片丢失、格式不支持、模型拒绝和解析失败必须进入例外清单；
5. 旧格式附录应统一到当前双段格式，或显式保留兼容原因。

### 6.2 输出身份

每个图片附录至少记录：

- 原文路径和图片相对路径；
- 图片序号、MIME、字节数和内容 SHA-256；
- Davybase 完整代码 commit、run ID、输入 tree、模型/provider、提示版本与完整提示 SHA-256、确定性参数、生成时间；
- 原始响应或合规留存的响应哈希、输入哈希和输出哈希；
- 类型、文字/结构转录、关键词；
- 成功、过滤、失败或人工复核状态。

图片指纹必须基于内容哈希，不只使用文件名和大小。

无图文档的文本摘要逐文档使用同一审计 envelope：Davybase 完整代码 commit、run ID、输入 tree、正文 SHA-256、提示版本与完整提示 SHA-256、模型/provider 与参数、输出 SHA-256、成功/失败状态和生成时间。文本摘要与图片附录的 run manifest 使用同一 schema 版本。

模型服务可能无法逐字重放同一输出，因此本合同要求输入、配置、代码和结果可审计，不承诺生成文本逐字可复现。

### 6.3 可信边界

图片解读是 L1 机器语义层：

- 可用于搜索、聚类、发现和预判；
- 不得单独证明正式数值、公式、因果关系和会计口径；
- HIGH 候选使用图片数字时，必须回看原图；
- 正式知识卡使用数值时，还需核对原文或更高权威来源；
- 图片模糊、裁切或多页关联不清时必须降级为 `uncertain`。

## 7. 四级证据模型

| 等级 | 内容 | 可以驱动什么 | 不可以驱动什么 |
|---|---|---|---|
| L0 来源登记 | 原文件、路径、URL、哈希、截面 | 可追溯目录 | 不能形成知识结论 |
| L1 机器语义 | 文本摘要、图片解读、自动主题路由 | 检索、聚类、候选发现 | 不能直接修改产品或正式规则 |
| L2 审查综合 | 回读原文后的知识卡、手册、方法模式 | 设计输入和候选方案 | 不能绕过决策改变范围/优先级 |
| L3 正式采用 | 被 accepted/amended decision 或 approved specification 明确引用的 L2 资产 | 产品原则、合同、工作包 | 不能反向篡改历史证据 |

证据等级与采用状态是两个正交字段。静态 release 只证明知识资产已发布，不会把 L2 自动提升为 L3。所有产品设计引用必须能够从 L3/L2 回溯到 L1/L0；无法回溯的观点不得进入 canonical 资产。

## 8. 静态知识资产结构

新 release 继续沿用现有目录，但补齐以下资产：

1. **来源层**：全量 source baseline、coverage、增量清单、图片例外清单；
2. **知识卡片**：一项可复用概念或方法一个版本化文件；
3. **领域手册**：K1–K10 的结构性综述和适用边界；
4. **方法与模式库**：分析包、报告章节、图表模式、经营分析会、归因和补证模式；
5. **产品映射**：知识→产品对象→当前能力→缺口→任务→采用状态；
6. **决策输入包**：会改变目标、边界、顺序或验收的候选单独成册；
7. **发布资产**：release metadata、coverage、lock、SHA 清单和迁移说明。

FLOW 不复制完整公众号原文和全部图片。静态知识资产只保留必要摘要、规范化结论、定位符和合规引用。

## 9. 采用、拒绝与核验纪律

每个净新增候选必须分别记录 `evidence_level` 与以下一种 `adoption_status`：

- `published-l2`：已进入静态知识 release，但尚未成为正式产品决定；
- `adopted-l3`：已被正式决策或批准规格明确采用；
- `candidate`：有价值，但需要后续任务或授权；
- `duplicate`：被既有知识完整覆盖；
- `rejected`：不适用、营销性、低质量或与产品边界冲突；
- `official-verification-required`：公式、准则、阈值或行业基准需要官方来源；
- `internal-authorization-required`：涉及内部数据、内部流程或敏感信息；
- `uncertain`：图片或上下文不足，不能可靠判断。

任何阈值、行业参考值和因果解释不得因为多篇文章重复出现就自动升级为平台默认值。

## 10. 新知识 release 生命周期

### 10.1 发布 ID

使用 `flow-knowledge-YYYY-MM-DD.N`。日期对应新固定截面日期，不对应执行开始日期；`N` 是该日期下已存在 release 编号的最大值加一。构建重跑保持同一候选 ID 和内容寻址结果；只有候选被废弃后重新立项，或同日另一个不同截面建立时才递增。生成器必须拒绝覆盖已存在且哈希不同的 release 目录。

### 10.2 Candidate seal gate

候选封存前必须满足：

1. 新旧 Git tree 差异可重复；
2. 核心范围来源计数闭合；
3. HIGH 候选全部具备正文回读记录；
4. 图片失败和过滤数量闭合；
5. 每个 canonical 资产有 source refs；
6. 产品映射无孤立 `published-l2` 或 `adopted-l3` 项；
7. candidate release lock 和 SHA 校验通过；
8. 独立读者仅凭候选资产和仓库可以回答固定题集；
9. 候选状态为 `sealed`，但 `CURRENT_RELEASE` 保持旧值；
10. current/canonical 产品文档在该阶段不得预先改写为新 release。

### 10.3 战略裁决与 activation gate

S0 基于 sealed candidate 执行影响评估；S1 由用户裁决正式决策；S2/S3 只在 staging 中准备决策、current/canonical 文档、路线图和交接变更。随后由 K6 在同一个 FLOW 提交中完成：

1. 加入最终 release 资产；
2. 把获批 L2 资产与正式决策/规格建立 L3 引用；
3. 修改受影响的 current/canonical 文档；
4. 原子切换 `CURRENT_RELEASE`；
5. 运行全部 release、metadata、links、reader fixture 和路线图唯一性门禁。

执行顺序固定为：创建尚未推送的 K6 activation 提交 → V 在独立干净 checkout 对该提交执行完整复验 → 复验通过后才推送 → 等待远端 CI。若本地复验失败，该提交不得推送；若远端 CI 在推送后发现本地无法发现的问题，必须以新的非破坏性提交恢复整个 activation 一致性集合，优先对精确的 activation commit SHA 执行 `git revert`。回退至少同时恢复 `CURRENT_RELEASE`、release-dependent current/canonical 文档、路线图、L3 映射和 metadata；新 release 资产若保留，必须降回 sealed/inactive。回退提交重新运行与 K6 相同的全部门禁，禁止只修改指针，禁止改写历史或强制推送。

### 10.4 兼容性

旧 release 永久保留，不在原目录内改写。历史设计继续绑定其签发时的 knowledge release；只有 current/canonical 文档按影响评估切换到新 release。

## 11. 战略重基线流程

候选知识和战略修改之间设置硬门：candidate 未 sealed，不启动正式战略影响评估；用户未完成 S1 裁决，不修改 D052–D054 和 current 产品文档；K6 activation 未通过，不切换 `CURRENT_RELEASE`。

候选封存后按以下顺序审查：

1. **目标假设**：核心用户、首要任务、最终价值、人工责任；
2. **工作流**：月度周期、资料提交、校验、扫描、调查、补证、双版本报告和发布；
3. **专业底座**：指标、科目、公式、阈值、版本、知识和规则可见性；
4. **产品结构**：三层两模块是否仍成立；
5. **能力差距**：现有代码、规格和新知识蓝本的差距；
6. **执行顺序**：公开模块 C 级出口、内部工作台规格、行业指标包和 AI 问数后续的依赖；
7. **验收标准**：知识是否带来新的量化门槛或企业月度周期标准；
8. **决策裁决**：保留、修订、取代或新增决策；
9. **文档刷新**：同步唯一 current state 和唯一路线图。

### 11.1 不预设目标一定变化

重基线必须允许三种结果：

- **目标不变、执行细化**：新知识进一步证明现有方向；
- **目标不变、顺序调整**：例如内部工作台规格可提前，代码实现仍受门禁；
- **目标或范围修改**：必须提交新的正式决策，明确取代关系。

不得为了证明本轮扫描有价值而强行修改战略。

### 11.2 必审问题

- FLOW 是否应从“财务分析工作台”进一步表述为“月度财务经营分析周期工作台”；
- 指标、经营分析会、报告、监督四体系是否进入内部工作台目标模型；
- “概览→深挖→归因→行动”是否成为统一分析叙事；
- 报告是否仍是权威母版，还是月度分析周期/分析包才是更高层权威对象；
- 行业指标包、模板包和图表模式库的产品边界；
- 内部工作台规格设计能否与公开 C 级出口并行，而实现门禁是否保持；
- 图片知识能否支撑报告页面模式和反模式库，但不复制受版权保护的具体设计；
- 公开模块、AI 问数和内部工作台的资源顺序是否仍合理。

### 11.3 预扫描结论的临时等级

在 L2 回读和 candidate seal 前，第二截面借鉴项 #20–#24 一律视为 L1/candidate。图片转录数值、行业阈值、“行动明确型报告占比 8%”等量化主张在原图、原文或官方来源核验前不得作为产品事实。当前路线图中的“设计输入已备”应在 activation 批次订正为“预扫描候选，待 L2 回读和新 release 门禁”，或在完成核验后改写为准确的正式状态。

## 13. 跨仓责任与工具改造要求

### 13.1 责任矩阵

| 仓库 | 唯一责任 | 完成证据 |
|---|---|---|
| Davybase（`git@github.com:davyzhong/davybase.git`） | 图片/正文知识化代码、敏感目录门禁、可恢复批次 | 规范远端可获取的完整 commit；run ID；输入 tree；配置/提示哈希；覆盖、过滤、失败和重试 manifest |
| ObsidianWiki（`git@github.com:davyzhong/ObsidianWiki.git`） | 原文与知识化输出、writer 锁、稳定截面 | 规范远端可获取的完整 commit/tree；工作树清洁证据；稳定窗口记录；输出清单 |
| FLOW（`https://github.com/davyzhong/FLOW.git`） | allowlist 摄取、L2 综合、candidate/release、产品映射和战略重基线 | 固定上游完整 SHA；摄取清单；release lock；决策与文档门禁；CI 证据 |

上游提交必须推送到规范 remote 且能在干净环境获取，FLOW 才能把对应依赖标为 completed。三个仓库分别提交、验证和推送，不宣称跨仓原子提交。

本轮仍遵守单协调者串行接管：长批次可以作为已登记的后台进程运行，但同一 vault 同时只能存在一个 writer；其他 Agent 和自动化只能只读。任务恢复必须读取 run manifest 和最后完成点，不能另起第二个写任务。若要恢复多 Agent 并行，必须另行获得用户明确批准并重新定义文件所有权。

### 13.2 工具改造

现有工具存在旧基线和旧 release 常量，不足以支持第二次发布。实施计划必须包含：

1. `knowledge_release.py` 从配置/参数读取 baseline、扫描目录和 release ID，移除 2026-09-12 写死值；
2. `source_baseline.py` 支持 vault Git tree 差异、重命名和内容增强分类；
3. 新增或扩展知识化覆盖报告，区分无图摘要、图片摘要、失败、过滤和不适用；
4. 图片指纹改为内容 SHA-256；
5. Davybase 图片处理支持核心非微信目录，且保持敏感目录 fail-closed；
6. 文档门禁按 frontmatter `status` 与 `doc_type` 判定 current/canonical：`state/navigation/governance` 的 `current`、`product` 的 `canonical` 以及当前 active plan 必须引用激活 release；approved 历史设计保持签发 release，除非正式 successor 取代；
7. 所有生成器先输出 staging，审查通过后再写正式目录。

跨仓修改必须分开提交：Davybase 负责知识化能力和 Obsidian 输出；FLOW 负责静态摄取、知识发布、产品映射和战略文档。不得在一个仓库的提交中伪装另一个仓库已完成。

阶段 A：静态知识重建
K0 等待并验收 Davybase 长批次
→ K1 补齐非微信图片覆盖与失败收口

→ K3 建立全量差异与来源基线
→ K4 语义路由、HIGH 精读与知识综合

阶段 B：战略重基线与正式激活
→ S0 产品假设和能力差距审查
→ S1 决策提案与用户裁决
→ S2 current/canonical 文档重基线 staging

## 15. 验收标准

### 15.1 知识刷新完成

- 新 snapshot 可从 Git tree 重复恢复；
- 核心差异 universe 闭合：added/deleted/present 分母对账，path/body/enrichment 三个变化维度分别对账，并单列 unchanged；
- 全 vault 的 L0 目录覆盖完整；核心深度范围的 L1 语义覆盖完整；HIGH 候选 L2 覆盖 100%；
- 核心深度范围内所有含图文档均有成功、过滤、失败或不适用状态；
- 机器摘要不被标为官方或人工验证知识；
- 新 release 的 coverage、lock、SHA 和 manifest 全部通过；
- 旧 release 可继续验证；
- 无 Obsidian 环境的读者测试通过。

### 15.2 战略重基线完成

- 每个新知识簇都有 published-l2/candidate/duplicate/rejected/official-verification-required/internal-authorization-required 等处置；
- 对 D052–D054 给出逐项“保留/修订/取代”结论；
- 目标、范围、原则、能力地图、战略设计和路线图之间无冲突；
- 唯一 current state 和唯一执行路线图仍成立；
- 新增工作包具有依赖、验收和知识引用；
- 所有 current/canonical 产品文档指向新 release 或明确记录保留旧版本的理由；
- 独立规格审查和读者测试无未解决 P1/P2。

### 15.3 Coverage 合同

每份 coverage 报告必须同时给出 universe 定义、分母、分子、排除项和排除理由，至少包括：来源变化、文本摘要、图片解读、自动路由、HIGH 回读、MED/LOW 抽样、L2 资产、产品映射和失败例外。任何条目不得同时出现在成功、过滤、失败和不适用多个终态中。

停止条件包括：HIGH 漏检率超过 5%；任一知识域 MED/LOW 双审样本发现系统性误分；无法读取项超过核心分母的 1%；图片/摘要失败集中于单一来源、格式或主题；敏感内容被发送到外部模型。触发后不得用“失败项可能不重要”继续发布，必须修正规则并重跑受影响分层。

### 15.4 独立读者 fixture

仓库内新增版本化题集与结果文件。每道题至少包含：问题、期望结论、必需 source refs、允许的不确定性、禁止断言和评分规则。测试从没有 Obsidian、Davybase 和本地缓存的干净 FLOW checkout 执行；读者必须是未参与本轮综合、使用全新上下文的 Agent 或人员。

门槛为：题目可回答率 100%；必需来源链有效率 100%；未经支持的正式事实为 0；任何 P1/P2 理解歧义为失败。实施计划必须给出 fixture 路径、运行命令和证据输出位置。

## 16. 失败与降级

| 情况 | 行为 |
|---|---|
| Davybase 长批次未完成 | 不冻结；继续使用旧正式 release |
| 批次存在少量不可恢复失败 | 先做最小人工筛查；确认不含 HIGH 且未触发 §15.3 系统性停止条件后，登记例外、影响范围和原因，方可继续 |
| Obsidian 工作树无法形成干净 commit | 不建立新 snapshot |
| 图片解读与原图冲突 | 以原图为准，机器输出标 rejected/uncertain |
| 新增文章缺少来源或作者 | 可登记 L0，但不能升级为 canonical 知识 |
| 公式/阈值无官方依据 | 标 official-verification-required，不进入平台默认值 |
| 新知识与正式决策冲突 | 形成决策提案，保持现行决策直到用户裁决 |
| sealed candidate 验证失败 | 不进入 S0，不切换 CURRENT_RELEASE |
| activation 或干净环境复验失败 | 不推送激活提交；若远端 CI 已发现失败，以 `git revert` 或等价新提交恢复整个 activation 一致性集合并重跑全部门禁 |

## 17. 预期结果

本轮完成后，FLOW 应拥有第二个真正独立、静态、可复现的知识版本，而不是一份指向动态 vault 的摘要。产品团队和后续 Agent 可以只读取 FLOW 仓库，就知道：

- 可用的财务与经营分析知识有哪些；
- 哪些来自文字，哪些来自图片机器解读；
- 哪些已被审查和采用，哪些仍需核验或授权；
- 每项知识影响哪个产品对象和任务；
- 项目目标和路线图为何保留或改变。

该结果延续 D051 的核心原则：Obsidian 是常驻内部研究源，FLOW 的运行与计划依赖版本化静态知识，不依赖动态知识库。
