# FLOW 项目执行收敛与验收计划｜2026-09-25

> **For agentic workers:** 执行前先读 `AGENTS.md`、`docs/00_start_here/PROJECT_STATE.md`、
> `docs/50_plans/CURRENT_ROADMAP.md`、`docs/50_plans/EXECUTION_TODO.md` 和本计划引用的工作包；
> 按依赖顺序推进，每一阶段完成后独立验证、提交并推送。状态只更新到现有路线图、To-do 和工作包，
> 本文不作为第二份进度台账。

**目标：** 收敛大麦模拟数据实施线、财报质量验证线、知识库与项目状态文档，使每项完成声明都有可追溯的同一提交、验收证据和一致的权威状态；在不绕过质量门槛和数据授权的前提下，逐步达到 FLOW 的产品目标。

**方案：** 先修复当前验证与协作基线，再整合分支交付并校正唯一状态入口；随后完成 U4/C-level 报告质量出口和知识/数据扩充的剩余证据；最后在门槛满足且获得授权后启动内部工作台验证。模拟数据验证与真实/公开数据质量验证分开记账，不相互替代。

**技术与证据栈：** Git 分支/提交与 GitHub Actions；`scripts/check_docs.py` 文档门禁；现有 API、web、E2E、数据质量基准与隔离 Compose 验收工具；财报 oracle、holdout 与知识发布登记。

## 1. 基线、范围与原则

### 1.1 本计划依据的审查基线

本计划基于 2026-09-25 的只读审查快照：

- 当前工作分支：`codex/damai-logistics-data-audit`，审查 SHA `bdc57a9fdda2063d2a3618466e36225a8ef64ede`；开工前必须重新 `git pull --ff-only` 并复核分支与状态。
- 大麦实施分支：`codex/damai-logistics-implementation`，审查 SHA `f62cf8eaed007ce59f18e0fef14a7c82a628a9c9`；该 SHA 的 CI run `36105604310` 为 success。
- 审计分支 SHA `bdc57a9` 的 CI run `36024558891` 失败；多个依赖 MinIO 的 job 在 `make infra-up` 阶段报告镜像 `unauthorized`，因此该 SHA 的完整回归尚未得到有效验证。
- 两条工作线尚未收敛到 `main`；审查时 `main` 的 `PROJECT_STATE.md` 与 `CURRENT_ROADMAP.md` 均落后于后续分支事实。
- 审查时本地工作区存在未提交的 `HANDOFF.md` 修改与未跟踪的 `services/api/tests/security/test_route_policy_registry.py`。它们必须先确认归属和意图，不得覆盖、重置或顺手纳入无关提交。

若执行时实际 SHA、CI、分支或工作区与以上基线不同，以最新可验证状态为准，并先把差异记录到现有交接/执行台账；不得照抄上述快照作为现状。

### 1.2 项目目标与不可突破原则

- 产品最终目标仍是财务经分专员主导的企业内部月度财务经营分析工作台；AI 可完成大部分分析与证据组织，报告由经分专员审核发布。公开财报模块是独立模块和共享底座，不等于最终产品。
- 大麦物流是合成演示/回归数据。它可验证功能链路、覆盖与页面状态，不构成真实企业准确性、公开财报泛化或 C-level 出口证据。
- oracle 必须独立于被测抽取器；原始财报档案不可改写；所有质量失败必须显式记录，不能为通过门禁而降格、屏蔽或删除断言。
- 只有精确 SHA 上的适用测试/门禁通过，且相应状态文档已同步，才可声明对应范围完成。
- 计划范围、验收口径或先后顺序若需改变，先更新本文和相关正式状态/规格并提交推送，再开始受影响的实现工作。

### 1.3 本计划不授权的事项

本计划本身不授权生产部署、公开发布、真实企业数据读取、数据迁移、schema 变更、密钥/CI 配置修改、删除文件或重写 Git 历史。触及这些事项时须按项目红线另行取得授权；本计划只规定何时提出与如何验收，不代替所需批准。

```text
G0 安全开工与状态盘点
  └─ G1 审计分支基础设施与 CI 绿灯
       └─ G2 工作线收敛与同 SHA 集成回归
```

## 4. 分阶段执行方案

### G0：安全开工与状态盘点

**目的：** 防止旧分支、他人未提交改动或误判 CI 状态污染集成。

**步骤：**

1. `git fetch origin --prune`，按项目规则拉取当前分支；记录工作分支、HEAD、远端 HEAD、`git status --short --branch` 和相关 worktree。
2. 逐项检查 `HANDOFF.md` 修改与未跟踪安全测试的归属、内容、预期用途；只记录，不擅自丢弃或并入。
3. 查询两条远端工作分支最新提交和各自同 SHA CI；核实是否有新提交覆盖本计划基线。
4. 核实 GitHub 当前 `main` 与数据库迁移事实。迁移头 0029/0030 分属不同工作线的观察结果，必须由迁移文件、测试和运行环境分别验证后才能统一表述；不得推断或执行迁移。

**退出条件：** 基线记录有确切 SHA、工作区归属明确、目标集成分支有明确选择；未解决归属或迁移冲突时停在 G0。

### G1：审计分支基础设施与 CI 绿灯

**目的：** 让 P0–P5/安全审计工作线获得真实、完整的自动化验证，而非被基础设施失败遮蔽。

**步骤：**

1. 对最新审计分支 SHA 获取完整失败 job/log，确认 MinIO `unauthorized` 是镜像名、上游匿名拉取策略、镜像代理还是凭据/CI 环境原因；区分环境失败与断言失败。
2. 先检查项目已批准的容器镜像配置/可用镜像缓存/现有 CI 做法；若需改 CI、密钥或外部镜像源，先提交变更方案并取得所需授权，不能直接改 secret 或凭据。
3. 修复后重跑原失败 job 和全量 workflow；保留失败 run，不以新绿 run 覆盖其审计价值。
4. 在同一个完整 SHA 上核对 `static-python`、`static-web`、unit、contracts、migrations、API/integration、数据合同、dashboard、E2E 与模块边界等适用 job 均成功。

**退出条件：** 最新审计分支目标 SHA 的全量必需 CI success；若环境故障尚未解决，准确标记为“基础设施阻塞、代码验证未完成”，不得标绿。

**建议验证：** `gh run list --branch <branch>`、`gh run view <run-id> --json conclusion,jobs,headSha`，并保存 run URL、head SHA 与失败分类到已有交接/工作包证据区。

### G2：两条工作线收敛与集成回归

**目的：** 将大麦模拟数据交付与审计/质量改动放进一个可验证的集成状态，同时保留各自提交和证据。

**步骤：**

1. 以 G0 选定的基准分支为起点，比较 `codex/damai-logistics-implementation` 与最新审计分支的提交图、公共祖先、文件清单和冲突；不得假设两个分支可直接快进或互不冲突。
2. 先列出需要合入、挑拣或重放的提交及其测试证据；迁移、路由安全、前端与种子数据文件存在重叠时逐文件审查。
3. 采用项目允许的普通 merge/cherry-pick/新集成分支方式；不 rebase、不强推、不覆盖历史。凡涉及迁移/schema 的实际动作按红线先取得授权并有迁移方案。
4. 对合并结果运行文档门禁、后端/API、前端生产构建与单测、模块边界、适用 E2E、数据质量基准，以及大麦发行包和干净环境验收。
5. 为集成结果产生唯一 commit SHA；在该 SHA 上运行完整 CI，并检查没有“较早绿 SHA 代替最终 SHA”的情况。

**退出条件：** 两条工作线的纳入/不纳入清单可追溯，所需变更在目标分支集成，数据合同/迁移状态无未裁定矛盾，所有适用本地门禁与同 SHA CI 通过。

**大麦专项验收引用：** 以其工作包记录的确定性构建/seed/verify、19 项数据合同、8 页面 E2E 9/9 和隔离环境验收为回归要求；具体命令以最新版大麦工作包为准，不复制旧命令替代正式工作包。

### G3：权威状态、计划与知识 release 对齐

**目的：** 消除“代码已完成、计划仍待办”以及不同分支的知识与迁移状态冲突。

**步骤：**

1. 以 G2 集成后证据为准，更新 `PROJECT_STATE.md`、`CURRENT_ROADMAP.md`、`EXECUTION_TODO.md`、相关 work item 与 `HANDOFF.md`；完成项必须引用提交、CI、测试或正式外部裁决凭证。
2. 将 U8 已关闭事实同步到 To-do，移除或明确注明过时记录；将大麦工作包正文中仍称“不可灌库/未完成”的旧段落改成历史说明或删除过时结论，避免与 completed frontmatter 冲突。
3. 对 U4 状态准确区分“oracle 录入完成”“首次运行完成但不可比”“修复后的回归”“独立 holdout 泛化验收”四种状态。
4. 核验 M2 原子激活与用户追认凭证、`CURRENT_RELEASE`、源清单哈希、sealed candidate/正式发布记录及独立复验结果。当前指针仍为 `flow-knowledge-2026-09-12.1` 时，先查清它是否就是批准 release；若发布序号应更新，按知识发布流程执行，不得仅因计划写了“激活”而改指针。
5. 补充 `docs/50_plans/README.md` 与阅读入口，使新计划及实际权威关系可发现；若其他索引也有过时路径，按最小范围修复。

**退出条件：** 任一入口都不会把已完成项列为待执行，也不会把未完成质量门槛写成已通过；知识 release 与发布证据、索引、manifest/hash 一致；`python3 scripts/check_docs.py --phase m1` 通过，涉及知识发布内容时再运行 `--phase m2`/`--phase m6` 适用门禁。

### G4：U4 版式适配、回归与独立留出样本

**目的：** 修复已识别的不可比版式，同时保留可信的独立泛化验证。

**步骤：**

1. 阅读 U04 工作包、oracle register、三份 oracle 原文引用、首次 `holdout_runs/2026-09-24` 结果及当前抽取器实现；冻结原始失败证据，不覆盖首跑结果。
2. 按规格为 `cn_ashare_table` 增加“合并及公司”合版标题支持，并将年报页码提示区间参数化；先编写针对版式解析和页码范围的失败测试，再做最小实现。
3. 以三份已录入样本作为回归集重新运行全行比较，按口径差异、解析误差、披露缺失归因；要求明确可比率、未匹配原因和锚点/值错误，不以“没有异常”替代量化结果。
4. 另选符合 holdout 协议的新公司/报告作为盲留出样本。留出数据选择者或 oracle 录入者不得读取被测抽取器输出；登记来源、SHA、抽签过程、预期值和隔离边界。
5. 留出测试按冻结协议运行，保存完整输出、逐行差异与复核证据；若未达到工作包门槛则继续修复，不得回填预期值或把新样本转为训练集后仍称其为 holdout。

**退出条件：** 三个原样本回归符合 U04 工作包验收；新 holdout 满足独立性与预先批准的精度门槛；失败样本和归因完整保存；U04 工作包和路线图同步到证据支持的状态。

**验证原则：** 对应单测先红后绿；再运行 U04 全行基准及相关解析/API 测试；最后在干净环境复跑冻结的 holdout 流程。

### G5：公开财报 C-level 独立审查与出口裁决

**前置：** G2 集成稳定；G4 的 U4/holdout 证据达到工作包要求；L0/L1 及溯源/重述/性能/问数等既有证据在最终 SHA 上重新核验。

**步骤：**

1. 盘点 C-level exit 工作包的每项门槛和证据版本，尤其是盲评、holdout lottery、准确率、锚点有效性、公司级泛化及拒答/降级行为。
2. 安排非实现方独立 AI/人工交叉审查；审查方只拿到协议允许的输入，记录样本、方法、冲突及裁决。
3. 由用户/合规授权的第三方按既定抽签协议执行 holdout；该动作是外部依赖，执行计划不能冒充已授权或已完成。
4. 汇总并由指定决策者作 C-level Go/No-Go；若 No-Go，问题进入原工作包，修复后须重跑受影响证据。

**退出条件：** 工作包定义的 C-level 全部量化门槛通过，独立评审和 holdout 有审计证据，正式 Go/No-Go 决策落盘。单有 `1794/1794` 覆盖率不能独自构成 C-level 通过。

### G6：P3 来源扩张、溯源与知识收尾

**目的：** 完成与当前质量门槛相关的公开数据来源工作，但不将材料归档误报为系统能力完成。

**步骤：**

1. 对 ZTO 2026 H1 报告验证 PDF 哈希、页码和 `pdftotext` 输出；修复或选择稳定文本层后端，保留原始 PDF 不变。
2. 按 P3 工作包合同将 ZTO 数据抽取、入库、勾稽、来源页锚与 API/UI 使用链路纳入验证；运行相应数据合同和报告页面测试。
3. 完成真实来源链接方案的评审后，按已批准规格实现来源引用/页面回链；测试缺失来源和无效锚的显式状态。
4. 复核 Alibaba FY2019–FY2026 分部序列和重述映射，确认它在目标分支、manifest、来源证据与系统可见数据中一致。
5. 按 G3 知识 release 流程核对知识资产候选/封存/激活/独立复验；变更知识索引时重建 `inventory.tsv` 和 `sha256sums.txt`，仅在确有知识资产变化时执行。

**退出条件：** P3 工作包所列来源、抽取、勾稽、引用、系统使用及测试均有证据；原始材料完整、hash 可复核；知识 release/index 无漂移。报告已归档或数据已扩充但未接入系统时，状态只能记为部分完成。

### G7：内部工作台与真实周期验证（门槛通过并授权后）

**前置：** G5 C-level 正式 Go；内部数据授权到位；用户批准当前内部试点范围及数据处理方式。未满足前置时本阶段保持 gated，不得使用合成数据伪装真实周期。

**步骤：**

1. 按内部工作台工作包先冻结月度周期、Finance BP 数据提交责任、经分专员审核发布职责、角色权限与数据合同。
2. 在授权数据和最小可行范围内验证持续企业空间、月度周期、报告版本、证据链、Finding/结论及人工复核流程。
3. 执行至少三个连续真实月度周期；每周期使用同输入人工基准，记录准确性、证据质量、人工投入/节省、失败/降级和用户反馈。
4. 依照战略重构设计中的量化标准和盲评协议进行独立评估，未达标则不宣称产品目标已实现。

**退出条件：** 内部工作台功能验收、连续三周期数据、对照基准、盲评与约定工时门槛全部通过，并完成正式业务 Go/No-Go。仅完成页面、接口或单次 demo 不等于最终目标达成。

## 5. 通用验证、提交与交接规则

每一阶段均遵守以下收尾协议：

1. 先运行阶段内定向测试，再运行受影响模块回归、文档门禁和 `git diff --check`；记录确切命令、退出码、测试数量与 SHA。
2. 检查 `git status`/差异，只暂存本阶段文件；保留所有预存用户改动，不做宽泛 `git add -A`，除非已逐项确认全是本阶段文件。
3. 以准确的 conventional commit 提交；立即推送当前分支。推送失败须报告明确原因，不静默搁置。
4. CI 必须针对最终提交 SHA 完成。CI 失败分类为代码失败、测试失败、基础设施失败、外部依赖失败；基础设施失败不算代码通过，也不自动算代码失败。
5. 更新 `CURRENT_ROADMAP`/`EXECUTION_TODO`/相关工作包/HANDOFF 中适用内容，并保持任务完成状态只有一个权威来源。
6. 交接必须包括：当前 branch/SHA、最后绿 CI run 与 SHA、完成证据、未完成/被阻塞项、用户授权依赖、精确续接文档和下一步。

推荐文档门禁：

```bash
python3 scripts/check_docs.py --phase m1
```

知识来源基线/发布或完整文档入口发生变化时，根据其变更范围追加：

```bash
python3 scripts/check_docs.py --phase m2
python3 scripts/check_docs.py --phase m6
```

其他测试命令必须以最新相关工作包、Makefile 和 CI workflow 为准；不得从旧计划复制已变更的入口。

## 6. 暂停与升级条件

出现以下任一情形，暂停受影响阶段并在交接中登记，不做静默绕过：

- 目标分支或最终 CI SHA 不清楚，或有其他 Agent 正在改同一文件/数据库；
- 用户已有未提交改动归属不明，或合并会覆盖它们；
- MinIO/数据库等基础设施问题阻止适用验证；
- 发现迁移/schema 变更、CI 凭据/密钥调整、生产/公开发布、真实数据使用或原始档案改动需要本计划未授予的权限；
- oracle 独立性、holdout 隔离或知识来源可追溯性被破坏；
- 测试只能通过减弱断言、屏蔽失败或跳过实际路径才能变绿；
- 工作包/正式规格的验收标准与本文或最新产品决策不一致。

## 7. 最终项目完成定义

只有同时满足以下条件，才可对外或在 README/PROJECT_STATE 中表述“FLOW 项目目标已达到”：

1. 公开财报 C-level 出口按正式协议通过，含独立交叉审查和独立 holdout；
2. 企业内部工作台在授权真实数据上通过功能、权限、证据与报告发布验收；
3. 连续至少三个真实月度周期通过同输入人工基准和独立盲评，达到既定质量和节省工时门槛；
4. 最终目标分支同一 SHA 的必需 CI 与隔离环境验收通过，相关文档门禁通过；
5. 项目状态、路线图、To-do、工作包、知识 release 和 HANDOFF 互相一致；所有外部依赖、限制和已知缺陷均有明确处置。

大麦合成数据演示交付即使全部绿，也只满足演示/回归数据工作包，不单独满足以上最终完成定义。

## 8. 中断续接

任何会话中断时，接手者依次：

1. 执行 `git status --short --branch`、`git log -1 --format='%H %cs %s'` 和 `git fetch origin --prune`；按项目规则同步当前分支。
2. 读取 `PROJECT_STATE.md`、`CURRENT_ROADMAP.md`、`EXECUTION_TODO.md`、本计划、当前目标工作包和最新 `HANDOFF.md`。
3. 依据最近一次已推送提交与同 SHA CI/证据判定最近完成阶段；不可仅凭本计划文字假定其已完成。
4. 检查是否有未提交用户文件或并行 Agent；未归属的修改保持原样并先确认。
5. 从首个仍未满足退出条件的阶段继续；若前置条件失效，回到该前置阶段，不跳级。
